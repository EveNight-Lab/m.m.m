## 코드 작성 원칙

### 1. 컴포넌트 중심의 구성
- **원칙**: 기능별로 독립적인 컴포넌트로 분리
- **규칙**:
  - 재사용 가능한 컴포넌트는 `components/` 폴더에 분리
  - 페이지별 컴포넌트는 `pages/` 폴더에 분리
  - 하나의 컴포넌트는 하나의 책임만 가져야 함
  - 컴포넌트는 가능한 작고 집중된 기능을 가져야 함

### 2. 중복 코드 최소화
- **원칙**: DRY (Don't Repeat Yourself) 원칙 준수
- **규칙**:
  - 반복되는 로직은 커스텀 훅(custom hook)으로 추출
  - 공통 스타일은 Tailwind 클래스나 공통 컴포넌트로 추출
  - 유틸리티 함수는 `utils/` 폴더에 분리
  - 비슷한 컴포넌트는 props를 활용한 재사용 컴포넌트로 통합

### 3. Tailwind CSS 중심 디자인
- **원칙**: CSS는 Tailwind 유틸리티 클래스를 우선 사용
- **규칙**:
  - 가능한 한 인라인 Tailwind 클래스 사용
  - 커스텀 CSS는 최소한으로 유지
  - 반복되는 스타일 조합은 `@apply` 또는 공통 컴포넌트로 추출
  - 반응형 디자인은 Tailwind의 반응형 접두사 활용 (`sm:`, `md:`, `lg:` 등)

### 4. 모바일 중심 개발
- **원칙**: 모바일 우선(Mobile First) 접근 방식
- **규칙**:
  - 모든 UI 요소는 모바일 화면에서 먼저 설계
  - 터치 영역은 최소 44x44px 유지
  - 모바일에서 스크롤이 자연스럽게 작동하도록 구성
  - Safe Area (노치, 하단 바) 고려 필수
  - `viewport-fit=cover` 및 `env(safe-area-inset-*)` 활용
  - 데스크톱은 모바일 레이아웃의 확장으로 고려

## AI 가독성을 위한 코드 구조 원칙

코드베이스가 커질수록 AI가 전체를 파악하기 어려워집니다. 다음 원칙을 따라 AI가 코드를 더 쉽게 이해할 수 있도록 합니다.

### 1. 명확한 폴더 구조
- **원칙**: 기능별/도메인별로 명확하게 폴더 분리
- **규칙**:
  ```
  src/
  ├── components/     # 재사용 가능한 UI 컴포넌트
  │   ├── common/     # 공통 컴포넌트 (Button, Card 등)
  │   └── features/    # 기능별 컴포넌트 (MonsterCard, BattleView 등)
  ├── pages/          # 페이지 컴포넌트
  ├── hooks/           # 커스텀 훅
  ├── utils/           # 유틸리티 함수
  ├── services/        # API 호출 로직
  ├── contexts/        # Context API
  └── types/           # TypeScript 타입 정의 (사용 시)
  ```
- **이유**: 폴더 구조만 봐도 코드의 역할을 파악 가능

### 2. 작고 집중된 파일
- **원칙**: 하나의 파일은 하나의 명확한 책임만 가짐
- **규칙**:
  - 파일당 200줄 이하 권장 (복잡한 로직은 더 작게)
  - 하나의 컴포넌트/함수/클래스당 하나의 파일
  - 관련 없는 로직은 분리
- **이유**: 작은 파일은 AI가 한 번에 이해하기 쉬움

### 3. 명확한 네이밍
- **원칙**: 이름만 봐도 역할을 알 수 있도록
- **규칙**:
  - 컴포넌트: `MonsterCard`, `BattleScreen` (명사 + 역할)
  - 함수: `fetchMonsterData`, `calculateBattleResult` (동사 + 목적)
  - 변수: `monsterList`, `isLoading` (명확한 의미)
  - 파일명: 컴포넌트명과 동일하게 (PascalCase)
- **이유**: 이름만으로도 코드의 의도를 파악 가능

### 4. 관련 코드를 가까이 배치
- **원칙**: 함께 사용되는 코드는 물리적으로 가까이
- **규칙**:
  - 같은 기능의 컴포넌트는 같은 폴더에
  - import는 사용하는 곳과 가까운 폴더에서
  - 관련된 유틸리티는 같은 파일이나 인접 파일에
- **이유**: AI가 관련 코드를 함께 읽기 쉬움

### 5. 일관된 패턴 사용
- **원칙**: 비슷한 기능은 비슷한 방식으로 구현
- **규칙**:
  - 모든 페이지는 `PageLayout` 사용
  - 모든 API 호출은 `services/` 폴더의 함수로
  - 모든 상태 관리는 동일한 방식 (useState, Context, 등)
  - 컴포넌트 구조를 일관되게 유지
- **이유**: 패턴을 알면 AI가 유사한 코드를 예측 가능

### 6. 명확한 주석과 문서화
- **원칙**: 복잡한 로직은 주석으로 설명
- **규칙**:
  - "왜" 이렇게 했는지 설명 (코드 자체는 "무엇"을 보여줌)
  - 복잡한 알고리즘이나 비즈니스 로직에 주석
  - 컴포넌트 상단에 간단한 설명 (필요시)
  - README에 주요 구조 설명
- **이유**: AI가 코드의 의도를 더 정확히 이해

### 7. 계층적 추상화
- **원칙**: 추상화 레벨을 명확히 구분
- **규칙**:
  - 낮은 레벨: 유틸리티 함수, 기본 컴포넌트
  - 중간 레벨: 비즈니스 로직, 복합 컴포넌트
  - 높은 레벨: 페이지, 주요 기능
  - 각 레벨이 명확히 분리되어 있어야 함
- **이유**: AI가 필요한 부분만 집중해서 읽을 수 있음

### 8. 타입과 인터페이스 활용 (TypeScript 사용 시)
- **원칙**: 데이터 구조를 명시적으로 정의
- **규칙**:
  - 모든 주요 데이터 구조에 타입 정의
  - 함수의 입력/출력 타입 명시
  - 공통 타입은 `types/` 폴더에 중앙 관리
- **이유**: 타입만 봐도 데이터 구조와 흐름을 파악 가능

### 9. 단일 진입점 패턴
- **원칙**: 각 기능/모듈은 명확한 진입점을 가짐
- **규칙**:
  - `index.js` 파일로 주요 export만 노출
  - 내부 구현은 숨기고 인터페이스만 공개
  - 관련 파일들을 하나의 폴더로 그룹화
- **이유**: AI가 모듈의 사용법을 빠르게 파악 가능

### 10. 점진적 복잡도 관리
- **원칙**: 단순한 것부터 복잡한 것 순서로 구성
- **규칙**:
  - 파일 상단에 간단한 것, 하단에 복잡한 것
  - 함수는 기본 케이스부터 처리
  - 컴포넌트는 props → state → effects 순서
- **이유**: AI가 코드를 위에서 아래로 읽으며 점진적으로 이해 가능
